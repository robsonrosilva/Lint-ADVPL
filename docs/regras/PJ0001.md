# PJ0001 — A referência do include diverge, na caixa, do nome real no disco

| | |
| --- | --- |
| **Identificador** | `PJ0001` |
| **Origem** | `projeto` — não existe no catálogo da TOTVS |
| **Grupo** | não se aplica (regra própria) |
| **Severidade no catálogo** | não se aplica |
| **Severidade exibida** | `Information` — **declarada** pela regra, por volume medido; ver abaixo |
| **Chave de configuração** | `advplLint.rules.PJ0001` |
| **Estado padrão** | **ligada** — decisão de 2026-08-20, com o número na mão |

## O que a regra pega

Uma diretiva de inclusão cujo nome de arquivo difere, **apenas na caixa**, do nome real gravado no
disco.

```advpl
// O diretório de includes guarda ACADEF.CH, em caixa alta.

#include "acadef.ch"    // reprova — o disco escreve ACADEF.CH
#include "AcaDef.Ch"    // reprova — o disco escreve ACADEF.CH
#include "ACADEF.CH"    // correto
```

O intervalo do diagnóstico cobre **apenas o nome do arquivo** — sem as aspas, sem a diretiva e sem o
caminho:

```advpl
#include "..\includes\acadef.ch"
//                    ~~~~~~~~~~   <- só isto é sublinhado
```

## Por que isso importa

Este é o defeito que justifica a existência desta extensão.

```
No Windows e no macOS padrão, o sistema de arquivos é INSENSÍVEL A CAIXA.
No Linux, onde o AppServer do Protheus roda, não é.
```

O desenvolvedor escreve `#include "acadef.ch"`, compila na máquina dele, funciona. Sobe para o
ambiente, e o AppServer Linux não encontra o arquivo. A falha aparece **longe, tarde e sem nenhuma
mensagem que ligue uma coisa à outra** — quem lê o erro de compilação no servidor não tem como saber
que a causa é a caixa de uma letra num fonte que compilou sem reclamar.

Medido no corpus de referência em 2026-08-19: **7% dos arquivos de include no disco têm maiúscula no
nome real**.

## Por que o TOTVS Code Analyzer não pega isto

Ele **não conhece o diretório de includes do projeto**. A verificação exige comparar o que o fonte
escreve com o que existe naquela árvore, e a árvore é de quem compila — não do catálogo.

É a justificativa obrigatória do Princípio III, e ela é literal, não retórica: sem o diretório, a
regra é impossível de escrever.

## Por que a detecção NÃO pode usar consulta de existência

Este é o ponto contraintuitivo da regra, e vale por escrito:

```
No Windows e no macOS, perguntar "o arquivo acadef.ch existe?"
responde SIM mesmo quando o disco guarda ACADEF.CH.
```

Uma implementação baseada em `stat`, `access` ou `exists` herdaria a cegueira do sistema de arquivos
e **a regra nunca dispararia nas máquinas onde ela é escrita** — que são justamente as máquinas onde
o defeito é criado.

O nome real vem de **listagem de diretório** (`readdir`), e só dela. É o que o índice de includes
faz, e é o motivo de ele existir.

## O que a regra NÃO pega

Os três silêncios, cada um com razão distinta:

| Situação | Por quê |
| -------- | ------- |
| O arquivo **não é encontrado** em diretório nenhum | "include faltante" é outro assunto, fora do escopo desta regra |
| A referência é **ambígua** — dois arquivos de mesmo nome, com caixas diferentes, em diretórios distintos | apontar um dos candidatos seria adivinhação, e a correção propagaria o palpite |
| O **índice ainda não está pronto** | ela não sabe a resposta, e a análise não espera pelo disco |

Os três levam ao mesmo silêncio na tela, por razões opostas. O terceiro é o mais importante: se a
regra disparasse com base num índice pela metade, ela acusaria divergência sobre arquivos que existem
e ainda não foram lidos.

A regra também **não** olha a caixa dos **diretórios** do caminho (`..\INCLUDES\acadef.ch`). Ampliar
para isso é regra nova, com fixture e medição próprias — não um ajuste desta.

E ela ignora referência que não é código: dentro de comentário de linha, de bloco ou de literal de
texto.

## De onde vêm os diretórios de include

De uma cadeia de precedência com recuo, resolvida no cliente, que para na **primeira fonte
utilizável**:

| Ordem | Fonte | Onde |
| ----- | ----- | ---- |
| 1 | `totvs.tds-vscode` | chave `includes` de `~/.totvsls/servers.json` |
| 2 | `killerall.advpl-vscode` | `includeList` do ambiente em `advpl.selectedEnvironment` |
| 3 | **chave própria** | `advplLint.includePaths` — definível por workspace |
| 4 | workspace | as pastas abertas no editor |

"Utilizável" significa **pelo menos um diretório que existe**, depois de descartadas as entradas
vazias. Configuração presente e vazia **recua** para a próxima fonte.

Para saber qual fonte está em uso e quais diretórios ela produziu, rode o comando
**"ADVPL Lint: mostrar os diretórios de include em uso"**. Sem ele, "a regra não dispara" e "a regra
dispara sobre a árvore errada" são indistinguíveis.

## Como corrigir

A lâmpada oferece a correção: ela troca o nome referenciado pelo **nome real lido do disco**, e não
toca na diretiva, no caminho nem nas aspas.

```advpl
#include "acadef.ch"    ->    #include "ACADEF.CH"
```

⚠️ **Esta correção fica FORA do "corrigir tudo" e da correção ao salvar, por padrão** — e isso NÃO
mudou quando a regra passou a nascer ligada. São duas decisões diferentes: apontar é barato, corrigir
em massa sem olhar não é. Trocar a diretiva é inerte; trocar o **nome do arquivo** muda o que o
compilador vai procurar, e aplicar isso ao salvar, no arquivo inteiro, propagaria um índice errado.

Quem confia no índice pode incluí-la:

```jsonc
"advplLint.fixAll.includeRules": ["CA3001", "PJ0001"]
```

## A decisão, com o número na mão

Princípio VI e FR-036: **sem taxa de disparo e de falso positivo medidas sobre o corpus, a regra não
entra ligada.** A medição foi feita em **2026-08-20**, sobre 1.012 fontes amostrados do corpus de
35.659, com o índice construído sobre os 35.103 arquivos de include do disco.

| O que foi medido | Resultado |
| ---------------- | --------- |
| Disparos na amostra | **1.445** |
| Fontes com ao menos um disparo | **738 de 1.012 — 72,9%** |
| Disparos por fonte | p50 **1**, p90 **3**, p99 **5**, máximo **8** |
| Nomes de include distintos envolvidos | **433** |
| O nome mais comum | `protheus.ch`, **559 disparos (38,7%)** |
| Amostra revisada à mão | **120** |
| **Falsos positivos** | **0 (0,00%)** |

Custo de análise, do mesmo relatório: **0,014 ms** no p50 e **0,21 ms** no p95 — abaixo do custo de
`CA3001` no mesmo corpus.

**Decisão: a regra nasce LIGADA, exibida como `Information`.**

### Por que ligada

Zero falso positivo em 120 casos revisados um a um, e o defeito é real em todos: uma referência que
não resolve no AppServer Linux. Uma regra com essa taxa que ficasse desligada por padrão seria uma
regra que ninguém veria — e o valor dela não é apontar quando pedem, é apontar antes de o fonte
subir.

### Por que `Information`, e não `Warning`

**O que decide a severidade aqui é o VOLUME, não a gravidade.** 72,9% dos fontes do corpus têm ao
menos um disparo. Como `Warning`, a regra inflaria a contagem de avisos de quase todo arquivo de um
projeto Protheus real — e o Princípio III é explícito sobre o que isso causa: regra que aparece em
todo lugar treina o usuário a ignorar o painel inteiro, e o dano é a extensão, não a regra.

É a mesma conclusão a que `CA3001` chegou, pelo mesmo caminho e com volume parecido (71,9%).

**`Information` não é "menos importante".** O painel de Problemas do VS Code lista `Error`, `Warning`
e `Information`. Ele **não lista `Hint`** — e foi assim que `CA3001`, rebaixada a `Hint` por volume
medido, sumiu da tela em 2026-08-19 e fez a extensão parecer quebrada. A lição foi aprendida com
custo: ao escolher severidade, confira como o editor **exibe** aquela severidade, não só quanto a
regra dispara.

Quem quiser tratar como aviso ajusta sem tocar em código:

```jsonc
"advplLint.rules.PJ0001.severity": "warning"
```

### A ressalva honesta

A regra depende de a cadeia de fontes apontar a árvore de includes **daquele** ambiente. Numa máquina
cuja cadeia caiu na varredura do workspace, ela pode apontar divergências vindas de uma árvore que
não é a de compilação — ruído de configuração, não de defeito.

A defesa é o comando **"ADVPL Lint: mostrar os diretórios de include em uso"**, que diz qual fonte
venceu e quais diretórios ela produziu. **Se a regra estiver acusando o que você não espera, rode-o
antes de desligá-la.**

**O que melhoraria isto**: uma forma de a extensão saber que a cadeia apontou a árvore CERTA — e não
apenas *uma* árvore. Enquanto isso depender de o usuário conferir à mão, esta ressalva fica de pé.

## Como desligar

```jsonc
{
  // Desliga a regra por completo
  "advplLint.rules.PJ0001.enabled": false,

  // Ou eleva a severidade, se o time quiser tratar como aviso
  "advplLint.rules.PJ0001.severity": "warning"
}
```

⚠️ Antes de desligar, rode **"ADVPL Lint: mostrar os diretórios de include em uso"**. Se a fonte que
venceu não for a árvore do seu ambiente, o problema é a configuração — e desligar a regra esconde o
sintoma em vez de resolver.

## Notas de implementação

- **Custo**: uma passagem pelas linhas da fatia. Em cada linha, pular o recuo e comparar uma palavra;
  só quando ela é `include` é que se procura o par de aspas. A consulta ao índice é um acesso a mapa.
- **Sem I/O no caminho de análise**: quem toca o disco é o índice, no seu próprio tempo. A regra
  recebe um mapa já lido, com consulta síncrona, e **não tem como esperar** por disco.
- **Índice sob demanda**: ele é construído na primeira vez que a regra precisa dele, nunca na
  ativação da extensão.
- **Atualização incremental**: criar, renomear ou apagar um include invalida **apenas o diretório
  afetado**. Renomear só a caixa — que é o conserto que o usuário aplica depois desta regra apontar —
  chega como apagar mais criar, e o índice enxerga.
- **Codificação e fim de linha**: o intervalo é calculado sobre texto decodificado como CP1252; bytes
  da faixa `0x80`–`0x9F` não deslocam a posição.
